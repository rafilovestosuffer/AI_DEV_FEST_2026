## 1. The Problem

Millions of low- and irregular-income Bangladeshis now have a mobile financial service (MFS) wallet in their pocket, but digital access has not given them financial control. Income arrives at one time of the month while household obligations arrive at another, so the wallet quietly drains through days 21–31; users discover the shortfall only in the last week, when the honest options have already narrowed to informal borrowing at high cost, or skipping essentials. The failure is one of *timing*, not of total income — a garment worker whose salary lands on the 7th and whose rent, food and family remittances stretch across the month can be fully "solvent on paper" and still run dry on the 28th. Today the only tool most wallets offer against this is a raw transaction list, which answers "what did I spend?" but never the question the user actually asks: **"will I run short before my next income arrives?"**

Two further costs compound the timing problem. First, habitual small cash-outs — withdrawing ৳500–1,000 from an agent several times a month because the wallet is used mainly as a cash-in/cash-out pipe — leak the agent tariff (modelled here at a labelled, configurable 150 bps with a ৳5 minimum) on money that often goes straight back to digital-capable merchants. Second, when users do try to plan (typically "save ৳30,000 in six months"), they plan with optimism rather than probabilities, and abandoned goals follow. We studied this through five synthetic-but-realistic personas — a salaried garment worker (the hero persona), a gig/ride-share driver with daily volatile earnings, a remittance-dependent household with lumpy inflows, a student with sporadic allowances, and a cash-heavy small shopkeeper — because these are exactly the customer segments Track 03 names: people who need to become *more financially capable*, not merely more active users.

## 2. The Idea

Sathi's idea is to turn the wallet's own transaction history into **foresight with honest trade-offs, in the user's own language, with every decision kept in human hands**. Instead of another budgeting app that categorises the past, Sathi predicts the shape of the *next three weeks* of the user's liquidity — as a distribution, not a point estimate — and reduces it to the three things a person can actually act on: one defensible **safe-to-spend** number for today, one calibrated **probability of running short** before the next income, and a small set of **quantified options** (actions, goal plans) whose trade-offs are computed, not asserted. The design stance is deliberately conservative for a financial product: the AI forecasts and explains, deterministic engines do all arithmetic, nothing moves money, nothing is auto-executed, and every figure on screen carries its evidence and its assumptions.

The Track 03 framing — "how might an MFS platform help customers become more financially confident and independent, not merely more active users?" — is answered by shifting the product's centre of gravity from transactions to *timing literacy*: the user sees when money arrives, when it leaves, when the trough comes, and what changing one habit does to the risk number. Confidence comes from calibrated honesty: Sathi would rather say "we cannot yet attain 80% recall at 60% precision at this rare-event base rate" than show a tuned number, and the evaluation in §6 reports exactly such a miss.

## 3. The Implemented Solution

The shipped system is a working, deployed product, not a slide. The deployable app is a Next.js 16 (App Router, React 19, strict TypeScript) serverless application with **35 API routes and 45 method handlers**, a bilingual (বাংলা/English) mobile-first UI with seven views, Prisma-backed SQLite storage with an optional Turso/libSQL adapter for durable hosted data, and a Capacitor Android shell (release-signed APK built by CI) that loads the live deployment and falls back to a fully on-device offline core when the network is unavailable. The offline core is not a splash screen: it bundles each persona's transaction history inside the APK and runs the deterministic engines — recurring-stream detection, a seeded block-bootstrap path simulation (200 paths, 5-day blocks), safe-to-spend, shortfall explanation and a goal Monte Carlo — on the device, with no backend and no internet.

Alongside the app, the repository contains the **offline ML factory**: a Python 3.11 pipeline (`data_gen/` → `ml/` → promoted artifacts) that generates the seeded synthetic panel (2,000 users across 5 personas × 12 months, plus a 500-user drifted cohort that is never trained on), trains the forecaster, calibrates it, and emits every published metric into `docs/metrics/*.json`. A FastAPI reference backend reproduces the same `/api/v1` contract the web app serves, so the TypeScript product and the Python reference are behavioural twins. Quality is enforced, not claimed: **98 pytest tests and 102 TypeScript tests** run in GitHub Actions on every push, together with lint, strict type-check, production build and a signed-APK workflow; the TypeScript LightGBM predictor is verified **bit-identical** to the Python booster on a 9-model × 24-row fixture (diff 0). Deployment is live at <https://sathi-pied.vercel.app> with zero-config serverless SQLite, seeded on first request.

## 4. Key Features

Sathi's capabilities are organised around six verbs. **Understand:** a deterministic categorizer with a per-transaction reason trace classifies history into 12 bilingual categories, and a recurring-stream detector learns salary, rent, bills and supplier rhythms (monthly 25–35-day intervals plus weekly/fortnightly cycles, each passing explicit date- and amount-stability tests) directly from the user's own data. **Predict:** the cash-flow view shows a 7-day shortfall risk as a calibrated probability with a p10–p50–p90 fan (the API serves 21 days of balance quantile bands), the projected trough day, and expected inflow/outflow — always labelled "an estimate, not a certainty". **Protect:** safe-to-spend is computed from the *simulated liquidity paths* (Q₀.₁₀ of the minimum balance minus the personal floor) rather than a static buffer, so the number reflects the user's actual income timing; the rule formula stays visible beside it. **Plan:** goals get a Monte Carlo plan (2,000 paths, common random numbers) with Wilson 95% intervals and three honest option types — extend the timeline, fix a monthly amount, or fix a probability — including the option "not feasible at this contribution". **Explain:** every insight-bearing response carries an evidence block (data window, model version, labelled assumptions, config hash), "Why this risk level?" factor lists, SHAP attributions, and a copilot answer whose numbers can be expanded to their provenance in one tap. **Own your data:** onboarding is an explicit choice (personal ledger or demo personas), the chat history and optional personal OpenRouter key stay in device-local storage, a double-confirmed reset deletes everything, and every capture, forecast and query is appended to an audit trail.

Two features deserve special mention because they close the loop from prediction to action. **Counterfactual actions** rank two or three candidate moves — trim the top trimmable spending category by 20%, batch the habitual small cash-outs (fee savings computed from the labelled tariff), hold a one-week payday buffer — by re-running the *same* simulated liquidity paths with each action's deterministic cash-flow delta and reporting the new shortfall probability; every shipped action card shows a negative risk delta, and nothing is ever executed automatically. **Natural-language capture** lets the user type `আজকে রিকশা ভাড়া ৮০ টাকা` and see a parsed transaction preview — amount, category, direction — before it is saved, achieving 100% amount and 100% category accuracy on the labelled holdout while never guessing silently.

## 5. AI Approach

The forecasting core is a **LightGBM quantile ensemble**: nine gradient-boosted tree models (p10…p90, pinball loss) trained as one *global, scale-free* model across all users — targets are divided by each user's 90-day mean gross flow, so a single model serves every income level and no income information is required at inference. The model predicts only the *irregular* component of daily net flow; scheduled money (salary, rent, bills) is handled by the recurring-stream detector and sampled with its observed jitter, which keeps the trees focused on what is genuinely uncertain. Inputs are 30 leakage-safe features computed strictly before the forecast origin — no persona label, no user id, no ground-truth column ever enters (enforced by tests on both stacks). Calibration is fitted on held-out users only: split-conformal widening of the p10–p90 band, a within-week path correlation ρ = 0.4 so that bad days cluster the way they do in real wallets, and a Platt map that converts simulated path frequencies into the served P(shortfall). At serving time, 400 correlated balance paths yield the shortfall probability, the trough distribution, the safe-to-spend quantile and the counterfactual deltas as functionals of one coherent forecast.

The LLM layer is architected around a single non-negotiable: **the LLM never computes money.** It routes intent and narrates deterministic engine results through a slot protocol — it may only reference figures through `{{fK}}` tokens that the application fills with pre-formatted, engine-produced values; any bare digit or number word (Bangla ০–৯ or English, including "পাঁচ হাজার" or "five thousand") in a draft fails closed to a reviewed bilingual template. A sanitizer blocks 14 prompt-injection patterns (English and Bangla) before any model sees the text, every request is rate-limited, and the deployed chat runs server-side through the z-ai SDK with an optional bring-your-own-key OpenRouter path that stays on the device. Grounding is backed by a BM25-lite retrieval over ten cited financial-literacy documents, so the copilot's advice is retrieved-and-verified rather than generated opinion. The result is a chat that can speak natural Bangla about money *because* it is never trusted with the numbers.

## 6. Results & Validation

All numbers below are generated by `ml/evaluate.py` on 300 frozen held-out test users (never used for training, early stopping or calibration) and served verbatim from the artifacts — none are hand-typed. On the main test set (2,325 user-weeks, shortfall base rate 3.1%), the model scores **Brier 0.0240** against the simple rule's 0.0529 (**BSS +0.546** — the model clearly beats the rule) but **ties the previous block-bootstrap baseline** (0.0236; bootstrap leads PR-AUC 0.410 vs 0.387 and recall-at-60%-precision 0.375 vs 0.236). We report that tie plainly rather than tuning it away. The model's edge is robustness: on the drifted cohort (3,808 user-weeks, base rate 5.6%) it leads everything — **Brier 0.0384 vs bootstrap 0.0413 vs rule 0.0657, PR-AUC 0.532 vs 0.476, recall@P0.6 0.460 vs 0.335** — and it degrades more slowly under ±10–30% feature noise. Forecast quality (T1): pinball 0.242 vs the best baseline's 0.255 (**+4.9%**), daily p10–p90 coverage **84.7%** against a nominal 80%. Reliability: ECE 0.012 (model) vs 0.014 (bootstrap).

Alert quality is stated per method at its validation-chosen cutoff, because each method trades recall and precision differently: the model recalls **50%** of shortfall weeks at precision 0.32; the bootstrap recalls 29% at precision 0.64; the rule's 66.7% recall is real but bought by over-alerting at **2.2× worse Brier**. The aspirational "recall ≥ 0.80 at precision ≥ 0.60" bar is **not attainable for any method at a 3.1% base rate** — the validation-chosen operating point (model recall 0.236 @ precision 0.57) is applied untouched to the frozen test and the miss is reported as-is. The goal planner carries the report's most uncomfortable finding: the raw Monte Carlo was **3–5× optimistic** (stated 10.5% → realised 2.8% over 875 back-tested goals), so the shipped P(goal met) passes through a Platt recalibration fitted on that frozen back-test, cutting expected calibration error from **0.099 to 0.020**. Fairness (T3) is audited per persona and per income band with the ugly numbers printed: the garment worker's PR-AUC is 0.690 where the overall is 0.387, and the shopkeeper cohort produced zero positive events (skill −3.138) — differences disclosed, not hidden. Explainability (T7) ranks the top SHAP drivers (user scale 30.7%, share of days without income 22.4%, day-of-month 10.5%), and the in-product risk classifier separately beats its simple rule (Brier 0.056 vs 0.066, PR-AUC 0.978 vs 0.880).

## 7. Real-Life Impact

For the user, impact is concrete and immediate: a garment worker who opens Sathi sees today's safe-to-spend (e.g., ৳318 with a ৳45 daily allowance), a 7-day shortfall probability she can act on days before the trough, the named week where the money runs out, and two or three moves whose effect on the risk number is computed in front of her. The three measurable levers a pilot would score are (a) **avoidable cash-out fees** per user, computed deterministically from the labelled tariff and auditable to the transaction; (b) **early-warning recall/precision** at a fixed, validation-chosen cutoff; and (c) **plan realism**, measurable as the calibration gap between stated and realised goal probabilities — the back-test instrument for all three already ships inside the product, since every served prediction is persisted as a `ForecastRecord` with its model version and factors. For an MFS platform, this is Track 03's differentiation in product form: the customer becomes more capable (foresight, literacy in her own cash-flow timing), more confident (probabilities that mean what they say), and more independent (her decisions, her trade-offs) — which is precisely what creates durable trust and engagement beyond payments volume. The deployment story is deliberately demo-honest: a live Vercel URL, a signed APK with a fully offline core for Bangladeshi network conditions, and a documented pathway from synthetic validation to governed real data (retrain and re-evaluate is one command; the splits are by user, so outcome scoring against `ForecastRecord` is a schema, not a rewrite).

## 8. Limitations & Responsible AI

The headline limitation is stated first: **every metric in this report is simulated** — the seeded generator injects the patterns the model learns, so the numbers are pipeline sanity checks, not accuracy claims about real customers; the label "SIMULATED — synthetic data only" is carried in every artifact and API response, and real validation requires governed data. The rare-event structure is the second honest limit: with shortfalls in 3.1% of user-weeks, Brier and PR-AUC values are small by construction, per-persona positives are sparse, and alert-level recall/precision carry wide error bars — which is why baselines are always served beside the model and losses are reported as readily as wins. Third, the deployment is demo-grade where stated: the serverless demo keeps its SQLite in a per-instance `/tmp` (the Turso adapter is provided and tested for durable hosted data), and AI narration is optional — without gateway credentials the copilot answers deterministically and every feature still works. Responsible-AI controls are implemented and testable rather than aspirational: synthetic-only data with zero PII; a fairness audit whose uncomfortable rows are printed verbatim; SHAP, reason traces and evidence blocks for explainability; prompt-injection sanitizing and a numeric-parity validator that fails closed; rate limits and an audit trail; and no autonomous consequential decisions — Sathi never moves money, never approves or denies anything, and presents options, never commands. We believe a financial copilot earns trust exactly where its marketing would have earned suspicion: in the places it tells the truth about what it cannot yet do.
